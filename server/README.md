# Октоберфест: выдача EDA-промокодов

Это отдельный PHP 8.3-модуль для существующего статического лендинга. С 29.09.2026 он размещён на `parkskazka.ru` вне webroot: `/opt/parkskazka-oktoberfest/`. Нельзя копировать PHP в `/var/www/parkskazka.ru/oktoberfest/`: этот путь обслуживается как статический и может раскрыть исходный код. Браузер отправляет форму на `/oktoberfest-api/promo`; сервис сохраняет код в MySQL, синхронизирует UniSender и Bitrix24.

## Что проверено 29.09.2026

- Лендинг — HTML/CSS/JS; прежде опубликованная форма `/subscribe` синхронизировала только UniSender и не выдавала EDA-код.
- На основном сайте — PHP 8.3 + MySQL Moguta. До миграции таблиц EDA не было; в списке UniSender `219` уже было 4 контакта. По решению владельца старые контакты не нумеруются, новые коды начинаются с `EDA1`.
- `/oktoberfest/` находится в Nginx `location ^~ /oktoberfest/ { try_files $uri =404; }`. Поэтому PHP-модуль нужно размещать вне webroot и маршрутизировать отдельными точными location.

## Миграция

`schema.mysql.sql` создаёт три таблицы: постоянный счётчик кампании, промокоды и часовые лимиты запросов. В таблице промокодов есть отдельные статус, ID лида и время попытки синхронизации с Bitrix24. Счётчик и выдача кода выполняются в одной транзакции с блокировкой строки `FOR UPDATE`; номер не вычисляется из количества заявок. Уникальные индексы защищают код, порядковый номер, email и телефон внутри кампании. Миграция **не переносит и не нумерует старые заявки**.

Перед развёртыванием были созданы резервные копии файлов, Nginx и MySQL в `/var/backups/oktoberfest-release-20260929-1aBVbGjj/`. Миграция применена к `parkskazka`, счётчик сразу после релиза равен 0, заявок в новой таблице 0. Для последующей проверки:

```sql
SELECT last_sequence FROM oktoberfest_campaign_counters WHERE campaign_key='oktoberfest';
SELECT COUNT(*) FROM oktoberfest_promos WHERE campaign_key='oktoberfest';
```

Исторические заявки не переносились и не получили коды по прямому решению владельца. Первый новый код — `EDA1`. Повторное применение миграции не сбрасывает счётчик; MySQL DDL выполняет неявный commit.

## Размещение и обслуживание

PHP-файлы размещены вне публичного каталога, с доступом выделенного пула PHP-FPM. SQL, тесты и `dev-router.php` не размещаются на сервере. В Nginx используются только точные маршруты API и запрет для остальных адресов `/oktoberfest-api/`:

```nginx
location = /oktoberfest-api/promo {
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME /opt/parkskazka-oktoberfest/promo.php;
    fastcgi_pass unix:/run/php/php8.3-fpm-oktoberfest.sock;
}
location = /oktoberfest-api/cashier {
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME /opt/parkskazka-oktoberfest/cashier.php;
    fastcgi_pass unix:/run/php/php8.3-fpm-oktoberfest.sock;
}
location ^~ /oktoberfest-api/ { return 404; }
location ^~ /oktoberfest/server/ { return 404; }
```

Перед изменением Nginx выполнен `nginx -t`; конфигурация была перезагружена. Кассирский путь закрыт парольной сессией, CSRF-токеном и лимитом попыток; он возвращает 503, пока пароль не настроен. Сессия истекает через 8 часов. Для реальной эксплуатации лучше выдать отдельные учётные записи кассирам через существующую систему авторизации; общий пароль — минимальная временная защита.

## Переменные окружения PHP-FPM

Обязательные: `UNISENDER_API_KEY`, `UNISENDER_LIST_ID` (отдельный список выдачи купона), `BITRIX24_WEBHOOK_URL` (входящий webhook с правами на чтение и создание лидов; HTTPS-адрес на `portal.parkskazka.com`), `OKTOBERFEST_RATE_LIMIT_SECRET` (не менее 32 символов), `OKTOBERFEST_CASHIER_PASSWORD_HASH` (результат PHP `password_hash`). Они не должны попадать в Git, JS, HTTP-ответы или логи. Дополнительно можно задать `OKTOBERFEST_DB_DSN`, `OKTOBERFEST_DB_USER`, `OKTOBERFEST_DB_PASSWORD`; иначе используется существующий `/var/www/parkskazka.ru/config.ini` Moguta. Путь к нему можно переопределить через `OKTOBERFEST_MOGUTA_CONFIG`. Последние 4 цифры телефона по умолчанию **не показываются** кассиру; после проверки политики обработки данных их можно включить через `OKTOBERFEST_CASHIER_SHOW_PHONE_LAST4=1`.

PHP-FPM обычно очищает окружение; перед запуском убедиться, что переменные доступны **самому пулу FPM**, а не только SSH-сессии. Секреты задаются во внешнем защищённом конфиге, не в репозитории.

## UniSender и письмо

В аккаунте UniSender заранее создать дополнительное поле с **переменной** `promo_code` и письмо/автоматизацию для отдельного списка. В шаблоне использовать `{{promo_code}}`. Метод `subscribe` получает `email`, `phone` при наличии, `Name`, `promo_code` через POST; `overwrite=2` обновляет только переданные поля, не стирая другие поля и теги. `double_optin=3` добавляет контакт без письма подтверждения; до запуска надо согласовать юридическое основание и убедиться, что отдельный список не запускает рекламные рассылки при незаполненном чекбоксе маркетинга. Вызов `subscribe` **сам по себе не отправляет** письмо с кодом — нужна настроенная автоматизация UniSender.

При ошибке UniSender запись и EDA-код остаются в MySQL со статусом синхронизации `pending`; API возвращает код и `delivery_pending=true`. Раз в 5 минут cron запускает `retry-runner.php unisender`, который получает секреты из root-only конфигурации и повторяет отправку. Лог содержит только класс сбоя или внутренний id записи, без API-ключа и контактов.

## Bitrix24 и цели аналитики

Обработчик ищет лид по паре `ORIGINATOR_ID=oktoberfest`, `ORIGIN_ID=application_id`; если его нет, создаёт лид с именем, почтой, телефоном и EDA-кодом. Атомарный статус `sending` не даёт двум одновременным запросам отправить один лид. При временной ошибке запись и код сохраняются, статус возвращается в `pending`; повтор выполняет cron-команда `retry-runner.php bitrix`. Перед повторным созданием она проверяет, не появился ли лид после неоднозначного таймаута. Вебхук хранится только в закрытой конфигурации PHP-FPM.

Ответ API содержит `bitrix_success` и `bitrix_new_lead`. Только комбинация `true`/`true` после подтверждения CRM запускает в браузере `ym(107188789,'reachGoal','send_get_sale')` и `_tmr.push({type:'reachGoal',id:3794718,goal:'send-get-sale'})`. Повторная заявка возвращает прежний код без нового лида и без новой цели отправки. При сбое Bitrix24 форма возвращает сохранённый код, но цель отправки не запускается; после фонового повтора CLI браузерную цель задним числом не отправляет.

`analytics.js` загружает оба счётчика только после выбора аналитических cookie. Три ссылки `data-discount-open` вызывают VK-цель `click-get-sale`. Модальное окно формы закрыто от Вебвизора классами `ym-hide-content`/`ym-disable-keys`; `noscript`-пиксели намеренно не добавлены, поскольку они обойдут выбор cookie. Для приёмки нужны реальные тестовые заявки на staging, сверка созданного лида и целей в отладчиках Метрики/VK; текущие автоматические тесты не обращаются к боевым сервисам.

## Локальная проверка без production-данных

Нужен PHP 8.3+ с PDO SQLite, cURL и расширением `pcntl` для параллельного теста:

```sh
php server/tests/run.php
php server/tests/http.php
```

Тест создаёт только временную SQLite-базу; в UniSender и Bitrix24 не обращается. Для ручной проверки HTTP можно создать локальную SQLite-базу из `schema.sqlite.sql`, установить `OKTOBERFEST_DB_DSN=sqlite:/абсолютный/путь/test.sqlite` и `OKTOBERFEST_RATE_LIMIT_SECRET`, затем запустить `php -S 127.0.0.1:8769 -t . server/dev-router.php`. POST JSON к `/oktoberfest-api/promo` без настроенных интеграций должен вернуть `{"success":true,"promo_code":"EDA1","delivery_pending":true,"bitrix_success":false,"bitrix_new_lead":false}` без секретов. Повторный POST с той же почтой должен вернуть `EDA1`; тестовый файл БД можно удалить после проверки. Касса — `/oktoberfest-api/cashier` при заданном хэше пароля.

API UniSender: https://www.unisender.com/ru/support/api/contacts/subscribe/ . Метод `subscribe` сохраняет контакты/дополнительные поля и требует отдельной настройки самого письма.

Условие акции по уточнению владельца — **10% на еду**, не на билет. Код погашается один раз; правила применения к позициям/чеку нужно согласовать с кассой отдельно. Реальную доставку письма и создание лида нужно проверить с тестовым адресом владельца; автоматизированные тесты не создают боевых контактов. Кассирский пароль пока не задан, поэтому внутренний интерфейс возвращает 503.
